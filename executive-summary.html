How a future valid submission must be made

These are instructions for a future selector-approved artifact. They are not permission to upload anything in the current repository.

  1. Resolve gates first. Supply the method lane and resolve the registry definition conflict explicitly. Confirm the current competition rules and any remaining weekly allowance in the authenticated submission page.
  2. Prove scientific merit. Use a visible-only buffered whole-segment hide-and-recover holdout; run every feature-alone leakage canary; beat a rebuilt current best under the same pooled evaluator, with withheld counts and a paired physical-block confidence interval. A projection is not a score.
  3. Prove distinctness in order. Compare the pre-placement surface to the registry; duplicate means stop before placement. Only if it passes, place dots and test the final dots. Log inaccessible registry entries as incomplete, never as unique. Do not exempt dense rasters without an explicit protocol revision.
  4. Package a normalized prediction through the shared writer. It must be single-band float32, values in [0,1], the template's CRS, shape and transform. There must be no NaN inside the footprint. The local all-finite export is conservative about range but its zero-outside convention is not verified organizer acceptance; reconcile it with the official null/NaN guidance first.
  5. Reopen and verify exact bytes. Run python scripts/validate_submission.py path/to/new-candidate.tif --out evidence/validation.json. Record the artifact SHA-256 and bind scientific, uniqueness and validator evidence to the same method and bytes. A local format PASS does not promote it.
  6. Separate selector decision. The selector, not this parallel lane, decides whether this artifact should use an available weekly slot. No auto-upload implementation is present. Do not treat a reserved filename as an artifact.
  7. Download the actual TIFF from a future enabled artifact link. A ZIP, if used, must contain only that one TIFF; no README, reports or extra rasters. Compare its SHA-256 with the adjacent receipt.
  8. In DrivenData, open competition 306 → Submit → New submission. Choose the exact .tif (or single-TIFF .zip if currently permitted by the form). Paste its unique submission name where the platform permits, and its adjacent note of at most 140 characters into Note (optional). Review the displayed remaining weekly quota before uploading.
  9. After processing, save the submission-page receipt, submission ID, displayed metric, timestamp and exact SHA-256. Only that binding warrants the label ORGANIZER-CONFIRMED for the artifact. Public team leaderboard rows alone cannot prove a named file's score. Save any rejection verbatim and retain the exact rejected bytes for diagnosis.
  10. Before the contest deadline, select only one final submission for both rounds, subject to the current official rules. Retain reproducible code, data provenance, license attribution and generative-AI-use disclosure.

Why the previous range error is not diagnosed here

Predicted values must be in range [0, 1] is consistent with an invalid numeric value, including a negative missing-data sentinel, but the rejected file is not available. It does not prove that NaN nodata caused the error. The official format text itself mentions null/NaN outside the bounds. Our shared writer rejects nonfinite/out-of-range arrays without silently clipping or replacing values, and independently reopens the written output. This prevents several local errors but does not promise portal acceptance.
